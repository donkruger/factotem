### Compatibility with v1.0

Every change in this PR is additive and must preserve the v1.0 Claude
path byte-for-byte:

- **Wizard flow.** First-time install (no agents in state, no
  pairings beyond the shared one) sees zero new screens. The
  shared-vs-new pairing prompt only renders when the operator is in
  H.5 add-agent mode AND `listPairings()` shows at least one
  non-shared option is *possible* (always the case once `pairings.ts`
  is in place, but the prompt itself doesn't fire on first run).
- **Telemetry capture.** Existing turns continue to insert
  `agent_turns` rows; the new columns get populated forward-only
  (older rows have NULL, which the dashboard renders as "—" rather
  than 0 to distinguish "no data" from "zero wait").
- **OneCLI delete.** Probe + delete are new endpoints; no existing
  endpoint changes shape. Banner only renders when the probe returns
  orphan candidates *and* the operator hasn't dismissed it this
  session.

## 2. Wizard add-pairing UI

The hardest of the three. Two interconnected concerns: the wizard's
step-machine needs a new branch, and the existing `whatsapp-auth.ts`
script needs to accept a non-default auth directory.

### 2.1 Problem

Today, when an operator runs the wizard's H.5 "Add another agent"
flow, they pick a provider and enter credentials, then jump to
Mounts. The new agent inherits the deployment's shared WhatsApp
pairing — meaning `@Ben` answers on Andy's phone number, dispatched
by `@<trigger>` in message text.

That's the v1.2.1 default and the right one for most operators. But
some operators want Ben on a *distinct* WhatsApp account — a separate
brand identity, a separate phone number, a separate contact list.
PR 9's backend supports this:

- `channel_pairings` table accepts arbitrary new rows.
- `WhatsAppChannel` instantiates one channel per row, each with its
  own auth directory.
- The dashboard's pairing dropdown surfaces the choice once both
  pairings exist.

What's missing: the wizard chrome that handles the **QR-pair the new
number** step. Today the operator would need to:

1. POST to `/api/pairings` to create the row.
2. Run `npx tsx src/whatsapp-auth.ts` directly (which writes to
   `store/auth/creds.json` — the *shared* pairing — overwriting it).

Step 2 is broken because `whatsapp-auth.ts` is hardcoded to the
shared auth dir. The wizard wrapper that operators use today
(`cli/claw-setup-gui/src/main/services/whatsapp.ts`) inherits the
same constraint.

### 2.2 Approach

Two parallel changes that meet in the middle:

1. **Make `whatsapp-auth.ts` per-pairing-aware.** Accept an env var
   `NANOCLAW_AUTH_DIR` (override the default `store/auth/`). The
   QR data + status hand-off files (`store/qr-data.txt`,
   `store/auth-status.txt`) also become per-pairing
   (`store/qr-data-<pairing_id>.txt`, etc.) so concurrent pairings
   don't clobber each other.
2. **Add the wizard branch.** Inside the GUI's add-agent flow, after
   `CredentialsStep` commits the new agent, the operator hits a new
   `PairingChoiceStep` (only shown in add-agent mode + only when at
   least one shared pairing exists, which is always true after
   migration). The choice:
   - **Use the shared pairing** (recommended) → agent's
     `channel_pairing_id` set to the shared pairing's id; wizard
     skips ahead to Mounts.
   - **Pair a new WhatsApp account** → POST `/api/pairings` to
     register the new pairing, run the QR flow against the new
     pairing's `auth_path`, then PATCH the agent's
     `channel_pairing_id` to the new pairing's id.

Don, in v1.2.1, decides to give Ben on Gemini his own WhatsApp
number. He launches the GUI wizard.

4. **PairingChoiceStep opens.** Two cards:
   - **Use shared WhatsApp** — "Andy and Ben both answer from this
     number. Operators address each by `@<name>` in message text."
     (Recommended, pre-selected.)
   - **Pair a new WhatsApp number for Ben** — "Ben gets his own
     phone number. Operators message Ben's number directly — no
     `@`-prefix needed in his groups."
5. Don picks the second option. The display-name input appears
   below: "Ben's WhatsApp". Phone-hint optional: "+27 82 …".
6. Click Continue → wizard:
   - POSTs `/api/pairings` with the kind/display_name/phone_hint.

## 3. Queue-wait telemetry measurement

Smallest of the three; pure backend wiring. Schema is in place
(PR 11). Insert path includes the fields (PR 11). What's missing is
the *capture* — recording the values at the moment a queued message
actually spawns its container.

### 3.1 Problem

Operators on multi-agent deployments occasionally see Ben lag —
several seconds between a message arriving and Ben answering. Today
we have no way to tell whether it's:

- **Container spawn latency** (network, image fetch, host I/O).
- **Provider latency** (Gemini's response time).
- **Queue contention** (Andy or a scheduled task held a slot).

Three measurable durations would disambiguate. `agent_turns` already
records `duration_ms` (the full turn) and `duration_api_ms` (the
provider's response time). The missing piece is *time spent waiting
for a queue slot* — between message enqueue and container spawn.

### 3.2 Approach

Capture two values at the moment `processNext` actually grants a
slot to a waiting message:

- `queue_wait_ms` — milliseconds between enqueue and spawn.
- `concurrent_at_spawn` — how many containers were already running
  when this one acquired its slot (sampled before the increment).

Thread both through the existing closure chain into
`insertAgentTurn`. No new schema. No new dependency injection
indirection. Three surgical edits.

The trick: `processMessages` (the entry point) wraps a callback that
becomes the queued work. We capture `queuedAt = Date.now()` in the
outer scope before the queue accepts the work, then close over it
when the work runs. `wrappedOnOutput` (which holds the
`insertAgentTurn` call) already runs inside that scope, so it sees
the captured values without any signature changes to `runAgent` or
the container-runner.

```
                Closure capture
                ─────────────────────────────────────────

  Inbound message arrives
        │
        ▼
  processMessages(channel, chatJid)
        │
        ├─ const queuedAt = Date.now();   // ← capture moment 1
        │
        ├─ queue.enqueueMessage(chatJid, async () => {
        │     const queueWaitMs = Date.now() - queuedAt;   // ← moment 2
        │     const concurrentAtSpawn = queue.getActiveCount();  // ← moment 3
        │     // ... existing run path ...
        │     // wrappedOnOutput closes over both values
        │     // and threads them into insertAgentTurn.
        │ });
```

### 3.3 File-by-file changes

**`src/group-queue.ts`** — expose the count via a public getter
(read-only — the queue still owns mutation):

```typescript
export class GroupQueue {
  private activeCount = 0;
  // ... existing private state ...

  /**
   * Read-only sample of how many containers are currently running.
   * Used by the spawn site to record `concurrent_at_spawn` in
   * agent_turns telemetry (multi-agent-completion § 5.2). Sampling
   * is a single read of the private counter — no race; the value
   * reflects the queue's state at this instant.
   */
  getActiveCount(): number {
    return this.activeCount;
  }
}
```

**`src/index.ts`** — capture timings around the queue's enqueue, and
thread them through the existing closure into `insertAgentTurn`.

*before* `queue.enqueueMessage`, `queueWaitMs` is computed *inside*
the queued callback (which is the moment the queue grants the slot),
and both values are captured by the same closure that wraps
`onOutput`.

```typescript
  // increments the counter. The value `0` means "this turn was the
  // first thing the queue had to do"; the value 4 means "four other
  // containers were already running when this one got its slot."

  // ... existing wrappedOnOutput closure already runs here ...
  // We capture the two values in the enclosing closure so that the
  // insertAgentTurn call (inside wrappedOnOutput) can read them.

  // ... existing runAgent call ...
});
```

add the two fields:

## 4. OneCLI delete-confirmation

### 4.1 Problem

When an operator deletes Ben (an agent), `deleteAgent` cascades the
groups + sessions to the default agent and drops the row. What it
doesn't do is remove Ben's OneCLI credential — the `Gemini` secret
stays in OneCLI's vault.

Per PR 11's design, this is intentional: credentials can be shared
across agents, so auto-deleting on first-agent-delete would orphan
the survivors. The probe (`GET /api/credentials/orphaned`) already
ships — it returns the credential names that are *no longer
referenced* by any agent.

What's missing: the dashboard surface that turns the probe output
into a one-click operator action, plus the destructive endpoint that
actually shells out to `onecli secrets delete`.

### 4.2 Approach

Mirror the **Repair Stack** typed-confirm pattern that Doctor uses
for destructive actions. Three pieces:

1. A new `DELETE /api/credentials/:name` endpoint that runs
   `onecli secrets delete <name>` via `runCommand`. Defensive
   re-check before the destructive call: refuse if any agent
   currently references the credential. Audit log entry written on
   success.
2. An `OrphanCredentialsBanner` component on `/agents` (and
   nowhere else — the banner is operator-prompted-cleanup, not a
   global system message). Polls `/api/credentials/orphaned` every
   30 s; renders a soft-amber card per candidate; click "Remove"
   → typed-confirm modal.
3. The modal asks the operator to type the credential name
   verbatim to confirm — same idiom as Repair Stack. Submit fires
   the DELETE; on 200 the banner shrinks; on error the modal stays
   open with the error inline.

### 4.3 Why typed-confirm (not just a button)

Two reasons:

- **Reversibility.** OneCLI delete is one-way — the credential is
  gone from the vault. The operator must re-paste it to re-create.
  A typed confirm raises the cost of the destructive click enough
  that it cannot happen accidentally.
- **Existing pattern.** The Doctor's Repair Stack action uses the
  same shape (`type "REPAIR" to confirm`). Operators trained on
  that surface read the same affordance the same way. We don't
  invent a new pattern just because it's a credential delete; we
  reuse the one that works.

### 4.4 File-by-file changes

**`src/http/api.ts`** — extend the credentials block with the
destructive endpoint:

```typescript
app.delete('/api/credentials/:name', async (req: Request, res: Response) => {
  const name = req.params.name;
  // Defensive re-check: refuse if any agent currently references it.
  // The probe at /api/credentials/orphaned should have already
  // filtered this out, but a race between probe and click could
  // sneak it through. Better to 409 than to leave an agent
  // unauthorised on its next spawn.
  const referenced = listAgents().some(
    (a) => a.provider.credential_id === name,
  );
  if (referenced) {
    res.status(409).json({
      error: `Credential "${name}" is still referenced by at least one agent. Reassign or delete those agents first.`,
    });
    return;
  }

  // Resolve onecli binary via existing path-resolution helpers.
  // PROVIDER_PLAYBOOK § 4.7 — never spawn by bare name.
  const onecliBin = findBin('onecli');
  if (!onecliBin) {
    res.status(500).json({ error: 'onecli not found on PATH' });
    return;
  }
  const r = await runCommand(onecliBin, ['secrets', 'delete', name]);
  if (r.code !== 0) {
    res.status(500).json({
      error:
        r.stderr.trim().split('\n').slice(-3).join(' · ') ||
        `onecli secrets delete exited ${r.code}`,
    });
    return;
  }
  const machine = getMachineIdentity();
  const auditId = writeAudit({
    machineId: machine.id,
    action: 'credentials.delete',
    target: name,
    payloadBefore: { name },
  });
  res.json({ ok: true, audit_id: auditId });
});
```

Note: `findBin` and `runCommand` live in `src/path-utils.ts` and
`src/subprocess.ts` (or equivalent). Use existing helpers, never

```typescript
  name: string,
): Promise<{ ok: true; audit_id: number }> {
```

**`dashboard/src/components/panels/OrphanCredentialsBanner.tsx`**
(new) — the operator-facing component:

```tsx
'use client';

import { useEffect, useState } from 'react';
import { Button } from '@/components/ui/Button';
import { Card } from '@/components/ui/Card';
import {
  deleteCredential,
  getOrphanedCredentials,
} from '@/lib/nanoclaw';
import { TypedConfirmModal } from './TypedConfirmModal';

const SESSION_DISMISSED_KEY = 'orphan-credentials-dismissed';

/**
 * OrphanCredentialsBanner — soft-amber card on /agents listing
 * OneCLI credentials no longer referenced by any agent. Per
 * multi-agent-completion § 5.1, we never auto-delete; the operator
 * confirms each removal via the typed-confirm modal (mirrors the
 * Doctor's Repair Stack pattern).
 *
 * Apple-philosophy heuristics applied:
 *   - One primary action per row — "Remove" button per credential.
 *   - Names beat IDs — the credential's display name renders as
 *     prose ("The Gemini credential is no longer used by any agent").
 *   - Reversible by default — typed-confirm raises the cost of the
 *     accidental click; the actual delete is one-way (the credential
 *     would need to be re-pasted via the wizard if regretted).
 *   - Dismissable per session so operators who deliberately keep
 *     orphan credentials around aren't nagged.
 */
export function OrphanCredentialsBanner() {
  const [orphans, setOrphans] = useState<string[]>([]);
  const [dismissed, setDismissed] = useState<Set<string>>(() => {
    if (typeof window === 'undefined') return new Set();
    try {
      const raw = sessionStorage.getItem(SESSION_DISMISSED_KEY);
      return raw ? new Set(JSON.parse(raw)) : new Set();
    } catch {
      return new Set();
    }
  });
  const [targetForConfirm, setTargetForConfirm] = useState<string | null>(null);

  useEffect(() => {
    let cancelled = false;
    async function poll() {
      try {
        const candidates = await getOrphanedCredentials();
        if (!cancelled) setOrphans(candidates);
      } catch { /* swallow */ }
    }
    void poll();
    const t = setInterval(poll, 30_000);
    return () => { cancelled = true; clearInterval(t); };
  }, []);

  function dismiss(name: string) {
    const next = new Set(dismissed);
    next.add(name);
    setDismissed(next);
    try {
      sessionStorage.setItem(
        SESSION_DISMISSED_KEY,
        JSON.stringify([...next]),
      );
    } catch { /* sessionStorage may be unavailable */ }
  }

  const visible = orphans.filter((n) => !dismissed.has(n));
  if (visible.length === 0) return null;

  return (
    <Card>
      <div className="space-y-3 border-l-4 border-[var(--color-warning)] p-4">
        <h3 className="text-sm font-medium text-[var(--color-ink)]">
          Unused credentials
        </h3>
        {visible.map((name) => (
          <div key={name} className="flex items-start justify-between gap-3">
            <p className="text-sm text-[var(--color-ink-muted)]">
              The <strong className="text-[var(--color-ink)]">{name}</strong>{' '}
              credential is no longer used by any agent. Remove it from
              the OneCLI vault, or dismiss to keep it.
            </p>
            <div className="flex flex-shrink-0 gap-2">
              <Button variant="ghost" onClick={() => dismiss(name)}>
                Dismiss
              </Button>
              <Button
                variant="primary"
                onClick={() => setTargetForConfirm(name)}
              >
                Remove →
              </Button>
            </div>
          </div>
        ))}
      </div>
      {targetForConfirm && (
        <TypedConfirmModal
          open
          title={`Remove "${targetForConfirm}"`}
          body={
            <p className="text-sm text-[var(--color-ink-muted)]">
              This deletes the credential from your OneCLI vault. If
              you later want to re-add an agent using {targetForConfirm},
              you'll need to paste the API key again via the setup wizard.
            </p>
          }
          confirmWord={targetForConfirm}
          confirmLabel="Remove credential"
          onCancel={() => setTargetForConfirm(null)}
          onConfirm={async () => {
            await deleteCredential(targetForConfirm);
            setOrphans((prev) => prev.filter((n) => n !== targetForConfirm));
            setTargetForConfirm(null);
          }}
        />
      )}
    </Card>
  );
}
```

**`dashboard/src/components/panels/TypedConfirmModal.tsx`** (new or
extracted) — the reusable typed-confirm primitive. If a similar
component already exists for Repair Stack, extract it here and

```tsx
'use client';

import { useState } from 'react';
import { Button } from '@/components/ui/Button';
import { Dialog } from '@/components/ui/Dialog';

interface TypedConfirmModalProps {
  open: boolean;
  title: string;
  body: React.ReactNode;
  confirmWord: string;
  confirmLabel: string;
  onCancel: () => void;
  onConfirm: () => Promise<void>;
}

/**
 * Typed-confirm modal — destructive-action gate. Operator types the
 * literal `confirmWord` to enable the primary button. The pattern
 * raises the cost of an accidental click without using a generic
 * "Are you sure?" dialog that operators dismiss reflexively.
 *
 * Mirrors the Doctor's Repair Stack confirmation idiom. Import this
 * from any future destructive action so the operator's mental model
 * stays consistent.
 *
 * Apple-philosophy: one primary action per screen, instant feedback
 * (button enables exactly when the typed value matches), reversible
 * by default (Cancel always available, Escape dismisses).
 */
export function TypedConfirmModal({
  open,
  title,
  body,
  confirmWord,
  confirmLabel,
  onCancel,
  onConfirm,
}: TypedConfirmModalProps) {
  const [typed, setTyped] = useState('');
  const [submitting, setSubmitting] = useState(false);
  const [error, setError] = useState<string | null>(null);

  const matches = typed === confirmWord;

  async function handleConfirm() {
    if (!matches) return;
    setSubmitting(true);
    setError(null);
    try {
      await onConfirm();
    } catch (err) {
      setError((err as Error).message);
    } finally {
      setSubmitting(false);
    }
  }

  return (
    <Dialog open={open} onClose={onCancel} title={title}>
      <div className="space-y-4">
        {body}
        <label className="block space-y-1">
          <span className="text-xs text-[var(--color-ink-muted)]">
            Type <strong className="text-[var(--color-ink)]">{confirmWord}</strong>{' '}
            to confirm
          </span>
          <input
            type="text"
            value={typed}
            autoFocus
            disabled={submitting}
            onChange={(e) => setTyped(e.target.value)}
            className="w-full rounded border border-[var(--color-hairline)] px-2 py-1 font-mono text-sm text-[var(--color-ink)]"
          />
        </label>
        {error && (
          <p className="text-xs text-[var(--color-danger)]">{error}</p>
        )}
        <div className="flex justify-end gap-2">
          <Button variant="ghost" onClick={onCancel} disabled={submitting}>
            Cancel
          </Button>
          <Button
            variant="primary"
            disabled={!matches || submitting}
            onClick={handleConfirm}
          >
            {submitting ? 'Removing…' : confirmLabel}
          </Button>
        </div>
      </div>
    </Dialog>
  );
}
```

## 7. Risks + gotchas

### 7.1 Wizard add-pairing — `creds.json` collision

The legacy `whatsapp-auth.ts` writes to `STORE_DIR/auth/creds.json`
on success. With the env-var override, a new pairing writes to
`STORE_DIR/auth-<id>/creds.json`. **Risk**: the operator's
`gitignore` covers `store/auth/` but may not cover `store/auth-*/`.

**Mitigation**: in PR 12, also update `.gitignore` to cover
`store/auth*/` (glob). Operators on customised forks regenerate the
gitignore via `/update-nanoclaw` skill.

### 7.2 Wizard add-pairing — phone-number reuse

If the operator tries to pair Ben's new pairing with the *same*
phone number Andy already uses, Baileys's pairing flow fails
silently — the existing session is invalidated. **Mitigation**:
detect this via the Baileys `connection.update` event during pair;
surface the failure in the WhatsAppStep's status with a copy hint
("Looks like this phone number is already paired with another agent;
pick a different number or remove the existing pairing first").

### 7.3 Queue telemetry — clock skew

`Date.now()` on the host is wall-clock — if NTP corrects mid-run,
the computed `queue_wait_ms` could be negative for a single turn.
**Mitigation**: clamp to >= 0 at the capture site:

```typescript
const queueWaitMs = Math.max(0, Date.now() - queuedAt);
```

Negligible but worth a one-line guard.

### 7.4 OneCLI delete — vault TOCTOU

The probe says "Gemini is orphaned" → operator confirms → in between,
another tab creates an agent referencing `Gemini`. PR 12's defensive
re-check in the DELETE endpoint catches this and returns 409. The
modal renders the error inline; operator sees the explanation and
can re-evaluate. No data loss.

### 7.5 OneCLI delete — credential typo on confirm

Operator clicks Remove on `Gemini`, types `Genini` (typo), button
stays disabled. Operator types correctly → submits. No edge case
here — the typed-confirm pattern is intentionally unforgiving to
exactly this kind of slip.

### 7.6 Wizard add-pairing — non-macOS QR rendering

The GUI wizard's QR rendering today reads `store/qr-data.txt` and
SVG-renders it. With per-pairing suffix, the file becomes
`store/qr-data-<id>.txt`. **Risk**: a stale QR file from a previous
pair-run leaks. **Mitigation**: the auth script deletes the QR file
on successful pair (already does so for the shared path); extend to
delete the suffixed file too. Belt-and-braces: WhatsAppStep wipes
the file on start to prevent stale-QR display.
